# AdventureCAD readiness: evidence and proposed work plan

Status: planning only; no runtime changes, builds, or tests executed. Evidence inspected from the current dirty checkout on 2026-11-08. Existing changes must be preserved. Source pointers are relative to AdventureCAD root and line numbers may drift.

## Verified architecture and blockers

1. The existing Mod API is substantial, but not a complete isolation boundary. `src/workstation/scripts/workstation_state.js:308` registers a mod, stores it in two registries, calls onInit, subscribes onCampaignLoad to campaignLoaded, subscribes **onCampaignRename** (singular) at line 329, and refreshes UI. Public helpers include getActiveTopology, refresh, saveActiveCampaign, registerMDIWindow (lines 357–369). Documentation calling this hook onCampaignRenamed is not the implementation contract.
2. Lifecycle duplication is a verified risk: `state_adapter.js:1257` directly invokes each onCampaignLoad and then emits campaignLoaded at 1271, which the registration wrapper also subscribes to. This can hydrate a mod twice. `selective_importer.js:997,1089` has direct invocation paths as well. `workstation_state.js:212` directly dispatches unload. Registration has no explicit replacement/unsubscribe cleanup in the inspected registerMod block. Furthermore, `promptLoadRuntimeModFile` (`workstation_state.js:375`) accepts `.js,.json` and executes `new Function(code)`, which is a footgun if a user selects a `.json` loot pack. Host team must remove duplicate direct loops in favor of canonical `CreatorStudio.emit('campaignLoaded', ...)`, gate dispatch on `isModEnabled(modId)`, and restrict runtime code execution to `.js` files.
3. `toggleMod` at workstation_state.js:340 updates disabledMods, persists global enablement, and refreshes UI. The inspected lifecycle loops do not demonstrate consistent enablement checks. Define disabled behavior explicitly; disabling must cancel pending mutations, close/disable windows, retain saved data, and leave accepted campaign items usable.
4. Existing item prototype collection deduplicates by name as well as ID (`entity_core.js:496`). That is unsuitable as the sole identity mechanism for cross-game items with the same name.
5. Existing promotion is **not repeated-drop instantiation**: `entity_core.js:971–982` returns an existing item with the same prototypeId; at 989–1000 it shallow-spreads the prototype and stamps node/status metadata. At 1025 onward promotion rewrites prototype references across the topology. Loot acceptance must not use that path blindly: repeat drops need separate IDs and must not retarget existing quest or pin relationships. New nested knowledge metadata must be deep-cloned.
6. Existing item possessions already inherit NPC location (`entity_core.js:9–18`); resource classification has special behavior (`:22–28`). Preserve these semantics and do not accidentally classify ordinary source loot as supply anchors. In addition, Sovereign Invariant #5 (`audit_campaign_quality.js:315-343`) requires 100% reciprocal crosslinks (`npc.carriedItemIds[]` <-> `item.ownerNpcId`, `node.itemIds[]` <-> `item.nodeId`, `quest.itemIds[]` <-> `item`), which `CampaignMutationEngine.upsertEntity` and `ENTITY_REFERENCE_DESCRIPTORS` do not currently maintain automatically for items.
7. Portable persistence is not arbitrary-root-field persistence. `campaign_exporter.js:112–117` and map_store.js:1502,1572,3158–3169 enumerate entity collections. `selective_importer.js:947–965` reconstructs known collections explicitly. Critically, on browser reload of any multi-map campaign, `workstation_state.js:786-895` (`initTopology`) hydrates from `creator_studio_maps_registry` + `creator_studio_campaign_entities` and returns early at line 894 without ever reading `creator_studio_active_topology` (`savedTopoStr`)! And `saveActiveCampaign` (`workstation_state.js:1216`) omits `extensions`, `deletedModules`, and `deletedPrototypes` from `creator_studio_campaign_entities`. `HOST-03` must persist and hydrate `extensions` (and `deletedModules`/`deletedPrototypes`) inside `creator_studio_campaign_entities` as well as all package formats.
8. Rename/Save As emit campaignRenamed in map_store.js:2913,3201. Save As explicitly clones known entity arrays at 3158–3169. Preset/history copying must be specified rather than inferred.
9. Offline build discovers mod.json and includes its entry at build_suite.js:1018–1069. Runtime HTTP fetching of source packs cannot be required under `file:///`. `build_suite.js` should support `injectDatasets` or pre-bundled JS pack registries so starter packs work zero-CORS out of the box.
10. Existing tests include item conflict/overwrite cases (`test/run_tests.js:458–520`). Master test phases are documented in scripts/test_suite.js:6–12: build, JS/syntax/import/cascade tests, campaign validation, wiki drift, loopback verification. Test-Suite.ps1 is a launcher with SkipBuild and Quick, not sufficient evidence that new contracts are covered.
11. Ticket authority is docs/agents/issue-tracker.md. Development sources are tickets/system/*.md; generated manifests/HTML must not be edited. Default new planning tickets use discovery and needs-triage. The coordinator should reserve IDs after checking existing files, not invent IDs here.

## Host-team scope and exclusions

Own stable item-reference and creation adapters, namespaced campaign extension persistence, lifecycle correctness, portable package preservation, optional generic knowledge presentation hooks, and contract tests. Do not own weighted rolling, source eligibility rules, starter game data, preset UI, simulation, or loot-specific migrations. Existing core item CRUD must continue working without the mod installed. Avoid a universal entity redesign; add the smallest generic boundary needed and document rejected alternatives.

## Proposed shared contract v1 (requires gate approval, not claimed to exist)

- Capability negotiation exposes a contract version and supported operations. A mod must show a useful unsupported-host message instead of mutating globals when capabilities are absent.
- Stable definition reference: `{ namespace, definitionId, revision }`; source game identity never depends on display name, installation path, or campaign ID. Existing prototype links can be an optional typed secondary reference. Missing definitions must resolve to a preserved snapshot, not an empty item.
- Host resolves existing item/prototype references read-only and accepts validated, immutable source knowledge snapshots. A definition is not automatically an active roster entity. The source-of-truth mapping is explicit; source pack knowledge remains mod-owned, existing native knowledge host-owned. Avoid a second authoritative copy except versioned snapshots for accepted instances.
- Generic batch item creation takes a campaign identity/revision guard, unique operation ID, item snapshots and optional stationing. It validates the entire request first, deep-clones nested data, assigns fresh instance IDs, applies one undoable atomic mutation, saves once and refreshes once, and returns created IDs or structured errors. Retrying an accepted operation must not duplicate items. Different drop operations from one definition may create multiple instances. Existing prototype promotion remains backward compatible.
- Namespaced JSON extension envelope, provisionally `campaign.extensions[modId] = { schemaVersion, data }`, supports get/replace through host APIs. Unknown namespaces survive loading/saving even when the corresponding mod is absent. Size limits and validation are explicit. Future schema versions are preserved read-only rather than overwritten.
- Campaign extension round trips cover browser persistence, creator.json, archive export/import, bound-directory sync, campaign rename, Save As, backup and selective merge. Selective merge policy must offer keep/replace/clone as appropriate, never overwrite target campaign-wide presets/history silently when importing only a map.
- Events carry immutable campaign identity and transition token. Exactly one load and unload delivery per transition; rename uses the implemented singular spelling or a documented alias without duplicate calls. Late registration receives a defined current-state hydration. Disabled/replaced mods have defined subscriptions and cleanup. Pending mod operations must reject if campaign changes.
- User global reusable presets use a separate library scope; campaign copies travel with campaigns. No campaign-specific settings stored under a single global key. Host owns storage transport; mod owns content semantics and migrations.

## Phased work and deliverables

H0 / baseline and contract discovery: capture git status and changed-path baseline; enumerate callers and persistence paths using graph; add a path matrix with supported behavior for each format; record existing test failures separately. Confirm real item fields/specs/notes and save behavior, not just ADR text. Deliver contract proposal and compatibility impact. Gate: mod team and coordinator approve fixtures and identity semantics.

H1 / lifecycle seam: normalize existing event paths and names, add unsubscribe/replacement behavior if needed, make disable and transition cancellation consistent. Target workstation_state.js, state_adapter.js, selective_importer.js, map_store.js. Gate: count-based load/unload/rename tests including new/open/import/switch/Save As/late-registration/re-registration; no duplicate listeners; existing mods unchanged.

H2 / persistence seam: introduce versioned namespaced extension transport and preservation in every supported campaign format. Inventory pack_engine.js, campaign_exporter.js, map_store.js, selective_importer.js, state_adapter.js and actual browser save implementation. Add migration only for schemas introduced by this work. Gate: fixture round trips preserve unknown namespaces, accepted item snapshots, missing-source references and campaign isolation; interrupted writes leave prior valid state recoverable. Read-only future schema survives export.

H3 / item bridge: implement reference lookup and safe repeated-instance batch creation via the existing mutation engine where possible. Include optional stationing and provenance metadata that existing renderers tolerate. Gate: repeated same-definition drops make distinct entities, no quest/pin retargeting, deep-clone independence, rollback on invalid item, idempotent retry, undo/redo as one action, stale-campaign rejection, normal native editing and possession still work.

H4 / integration fixture: run a tiny fake mod exercising only public contracts. Mod team can consume a matching mock adapter before host is complete. Gate: native API and mock execute the identical contract fixtures; no mod-private globals or DOM IDs needed to accept loot or persist settings.

H5 / release integration: coordinator merges source changes in controlled order, updates per-file wiki notes and approved specs, runs Build-Suite in the designated integration checkout, then full Test-Suite, targeted new tests, and UI smoke checks under offline file and loopback. Source-only team worktrees never build or commit compiled bundles. Gate: evidence bundle contains command results, known-baseline comparison, UI scenarios, migration/rollback instructions and a review signoff.

## Required test matrix

- Campaign A settings/history never enter B; switch during acceptance cannot commit to B.
- Name collision between games; missing optional native prototype; changed source revision; mod removed and reinstalled.
- Duplicate operation ID vs two separate legitimate repeats; five valid rows with one invalid row; disk/storage failure; undo then redo.
- Unknown mod state preserved without installed code; corrupt namespace quarantined with useful error; oversized payload refused; future version retained.
- Every documented package/save format round trip; selective map merge conflict; Save As changes campaign identity without damaging definition references.
- HTML/script-like item text rendered as text; imported data-only packs never evaluated as code.
- Existing sourcebook mods, item catalog, NPC possession, quest references, cascade deletion and canvas item badges remain correct.

## Risks, decisions and red-team gates

Verified highest risks are duplicate lifecycle delivery, name-based prototype dedupe, promotion reuse/reference rewrite, and root-field loss in explicit serializers. Persistence completeness is not yet proven for every actual save route; H0 must produce that proof. A comprehensive universal knowledge editor is not automatically required; reuse existing inspector plus a safe extensible details renderer unless evidence demands more. API names, extension envelope location, batch quantity representation, exact package merge UX, history bound, source content limits and update diff presentation remain contract design choices, not verified current capabilities.

Red team must challenge: can a disabled mod receive events; can two modules overwrite each other by name; can accepting one item update unrelated relationships; can an asynchronous callback write to another campaign; can unknown metadata disappear on a rarely used export path; can a shared object leak edits back into source records; can retry/undo duplicate items; can hostile imported text execute. Each finding needs severity, reproducer/fixture, owner, fix proposal and a retest gate. No P0/P1 findings or unresolved data-loss paths at implementation/release approval. Lower severities require explicit coordinator disposition with evidence.

Planning exit: approved common contract, separate host/mod ownership, bounded scope, mapped persistence paths, observable acceptance criteria, recorded open decisions and independent red-team review. This document grants no implementation authorization.

### Working rules and handoff

Host lead owns HOST-00 through HOST-06; coordinator owns contract arbitration and HOST-07 integration authorization. Within the host team assign one file owner at a time for shared persistence/event sources. Mod team must request a contract revision through the coordinator rather than modify host globals directly. HOST-02 and HOST-03 can overlap only with explicit ownership of shared files; conceptual independence does not make shared-file editing safe. Each package handoff includes changed paths, fixture results, known limitations, compatibility notes and commit/diff anchor. Do not use a successful mock test as proof of real persistence coverage.

Proposed decisions for the joint contract gate: choose namespaced versioned campaign transport; maintain source-defined immutable knowledge plus accepted snapshots; create distinct instances for repeated drops without changing prototype promotion semantics; preserve unknown state when mod absent; route all item acceptance through a generic atomic host boundary; standardize current onCampaignRename spelling with documented compatibility if required. These are recommended implementation decisions awaiting plan/contract approval, not additions already made to AdventureCAD.

Additional mandatory HOST-04 restriction: generic `CampaignMutationEngine.upsertEntity` must **not** implement drop acceptance through its current name-matching behavior. At `campaign_mutation_engine.js:467–493`, it resolves names/titles and, even if an ID is provided but not found, can fall back to an existing entity with the same name. A fresh generated ID alone therefore does not guarantee create-only semantics. Provide an explicitly create-only path with duplicate-ID rejection and zero name fallback; do not change general upsert semantics for unrelated callers without separate regression justification. Add fixtures where two different sources and two repeated result rows all have identical names, and verify independent instances plus unchanged existing same-name entity data.

Additional mandatory HOST-03 restriction: campaign-wide loot state must survive **map navigation inside the same campaign**, not just campaign save/reload. Existing `modData` usage can be map-scoped; its name is not proof of campaign scope. Add A-map1 → A-map2 → A-map1, then campaign B, then campaign A fixtures, including saves from each map and acceptance destinations on another map.
